## Evidence retained without rerunning it

The [13-case broker characterization](../reviews/2026-10-18-MAC-BROKER-CHARACTERIZATION.md) remains narrow evidence for the recorded signed single-root operations and denials. It does not prove a command supervisor, multi-root authority, coherent copy or conflict-safe replace/move/Trash.

The retained-capture fixture ran once, exit0, with 12 observations meeting its research oracles; the separate real-process supervision probe also exited0. Its report and raw artifacts remain the authority for hashes, identities and syscall results. Two observations directly constrain the next design:

- During concurrent writes, source states were `AAAABBBB`, `1111BBBB`, `11112222`, while copied bytes were `AAAA2222`. A resulting hash authenticates those copied bytes, not a coherent source version. Matching metadata or a best-effort read must not be presented as snapshot proof.
- A held directory descriptor continued capture/publication after an ancestor tree moved. Descriptor-relative I/O alone therefore did not confine access to the originally granted pathname boundary.

Open writable descriptors also continued modifying the retained inode after capture. Exclusive name collisions preserved the recreated entry in the tested cases, but did not produce immutable retained content, mandatory exclusion of external writers, or power-loss durability. The cleanup record includes EPERM whose cause is unverified; strict end-to-end60s compliance and the identity-check/unlink race remain unproven. These are evidence limits, not reasons to repeat valid tests now.

## Contracts still required before implementation

1. **Binding and revocation:** participating root identities/revisions, working/reference roles, overlap behavior and no widening; demonstrate behavior for root/ancestor relocation and existing handles. A polling check alone does not discharge §7.
2. **Copy and change detection:** choose coherent-source semantics and observable conflict behavior that protect user work under §4. Reference copy conveys no source-write authority. Define partial-output ownership and truthful failure outcomes.
3. **Retained mutations:** protected same-volume recovery outside command-writable project scope, retained-entry lifetime, late-FD writes, user recovery, actual namespace effects and APPLIED/CONFLICT/UNKNOWN receipts. Never hide capture-side effects as `file_mutated:false`; never overwrite concurrent edits during rollback or replay an unresolved operation.
4. **Move and Trash:** select their own recovery/outcome contracts. Capture followed by moving the retained entry consumes its recovery name; copying it changes inode/late-writer behavior. A private recovery directory is not native Trash. Cross-volume move remains unsupported until separately designed.
5. **Native runtime:** identify a concrete mechanism using the existing host/toolchain where possible; prove actual working-project edits, reference/outside/descendant denials, root replacement/revocation, private evidence/recovery storage, network limits and owned stop/reconciliation. A guest fallback would additionally need compatible image/platform/resources and share-boundary proof. Public API availability is not evidence these obligations hold.

These are research and contract dependencies within existing M1/P01, not new product milestones or connector permission prompts. M2/M3 acceptance remains separate. Windows work begins only after complete accepted M5; multiple independent projects on one host remain required, while no multi-machine matrix is added.
