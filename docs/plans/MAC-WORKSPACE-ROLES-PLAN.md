# Mac workspace/reference roles implementation plan

The user requested this scope revision and continued implementation on 2026-10-18. This plan defines the product contract and its verification; it does not claim those capabilities are already available through the plugin.

**Goal:** Give GSA explicit multiple-workspace/reference capability contracts before integrating full local tools through `gsa-lc-mac` / `gsa-lc`.

**Architecture:** Extend the existing registry with explicit roles and an atomic trusted enrollment API. Preserve legacy grants without interpreting their permission arrays as new full-workspace consent. This first change does not alter protected persistence, MCP binding, native files or command backends.

**Tech Stack:** Existing TypeScript ESM/Node >=20 and node:test; no dependencies.

**Spec:** [CRITERIA.md](../CRITERIA.md), authoritative 2026-10-18 scope and §§3/7; P02 in [implementation plan](GSA-LOCALCONNECTOR-IMPLEMENTATION-PLAN.md).

## Global constraints

- Mac first; no Windows development, new VM, installation or media writes.
- Preserve existing behavior outside this contract. Role metadata alone must not activate a backend or confer verified runtime capability.
- Reuse valid broker/retained-capture and other unchanged evidence; no full/native rerun for this source contract.
- Roles express intended capability, not OS confinement. Runtime operations remain blocked until their actual backend is verified.

## Why this revision

The user clarified that connector capabilities cover full workspace operations, including copy/rename/delete, while refs allow list/search/read/copy-out only. Older read-only binding plus separate execute enrollment cannot represent that intent. A small registry foundation is independently useful and does not wait for, or claim to solve, native shell confinement. Existing P01 characterizations remain evidence with their existing limits; M1 is not marked complete.

## Review focus

1. Legacy read or read/execute grants must retain exactly their prior permissions and never become full workspaces automatically.
2. Aliases, duplicate IDs/roots and opposite-role nesting must not silently widen authority or partially commit.
3. Failed batches and concurrent enrollment/revocation must leave the previous active grants and revision tombstones intact.
4. For grants created by the new explicit-role API, same-revision import is allowed only for an identical active grant; changed authority and revoked epochs are rejected. Unrelated legacy-only import behavior is not refactored in this task.
5. Directory replacement between preparation and commit must be rejected when observed; realpath/stat checks alone are not native race confinement.

## Task 1 — explicit roles and atomic registry foundation (implement now)

**Files:** modify `src/core/contracts.ts`, `src/core/workspace.ts`; create `test/workspace-roles.test.ts`. Existing `test/workspace-tools.test.ts` and `test/grants.test.ts` are compatibility checks, not files to weaken or rewrite. No server/grant-store/native changes.

**Interfaces:**

- Export `WorkspaceRole = "workspace" | "reference"` and `WorkspaceRoleRequest { readonly id: string; readonly root: string; readonly role: WorkspaceRole }` from contracts.
- Add optional `readonly role?: WorkspaceRole` to `WorkspaceGrant` so existing role-less source/durable grants remain valid. Explicit workspace role requires exactly read/write/execute; reference exactly read (set semantics). Reject inconsistent role/permissions on import. Role-less legacy grants retain their permission set without role inference.
- Add `WorkspaceRegistry.enrollRolesTrusted(requests: readonly WorkspaceRoleRequest[]): Promise<readonly WorkspaceGrant[]>`. Trusted contract only, not an MCP tool or proof of user consent. Accept 1–16 input entries, return one grant per unique ID in first-occurrence order. Validate runtime input values as well as TypeScript types.
- Keep existing `enrollTrusted`, `importTrusted`, `list`, `get`, `revoke`, `requireGrant`, `resolveExistingRead` call signatures compatible. Use existing ConnectorError codes: malformed/unverified metadata or epochs `SOURCE_UNVERIFIED`, bad/outside root `PATH_OUTSIDE_SCOPE`, authority/role overlap `PERMISSION_DENIED`; retain current invalid-ID behavior where compatibility requires it. No new wire error scheme.

**Binding semantics:**

- Resolve and pin every existing absolute directory before committing; observe canonical path plus device/inode. Relative, missing, non-directory or malformed entry rejects the entire batch, including revisions.
- Same ID/canonical root/role/identity repeated within a batch is one request. Same ID with a different root or role within a batch rejects. Different IDs for the same canonical root or physical identity reject, including symlink aliases.
- Against existing state, identical explicit active ID/root/role/identity is idempotent and retains revision. Explicit trusted reselection changing that ID's root/role/identity advances its revision once; it must not mutate another ID or expand another grant. Legacy-to-explicit conversion is permitted only through this new explicit trusted selection, never import/inference.
- Reject canonical ancestor/descendant overlap between opposite roles in either direction, against both proposed entries and retained active grants. Same-role nesting is allowed as separately selected roots. Legacy grants with write or execute count as workspace authority for overlap checks only; read-only legacy grants count as reference authority for this check only. This classification must not add a role/permission to legacy objects.
- Compare the final prospective set, so an old grant replaced in this batch does not create an artificial conflict. Validate the entire set before publishing it.
- Use a monotonic registry mutation generation or equivalent serialization: if awaited preparation overlaps another mutation, reject/revalidate against the current complete state before commit. No interleaving may resurrect a revoked ID, lose another grant or commit stale revision calculations. Recheck prepared directory identity before publication; document remaining filesystem TOCTOU limits.
- New IDs begin revision 1. Changed existing IDs increment from the highest epoch, including revoked tombstones. Reject overflow before mutation. Revocation must not allow a subsequent import to reuse its epoch.
- Revoking an ID while its explicit selection is still awaiting filesystem preparation cancels that pending selection, even if the ID has never been active. Revoking an unknown ID with no pending selection retains its legacy no-op behavior. A sparse or otherwise malformed request array must reject with the documented error and leave the registry unchanged.
- `importTrusted` validates explicit roles and overlap invariants too. For an ID with explicit-role history (or an incoming explicit-role grant), lower revision rejects; equal revision succeeds only when the active stored grant has identical canonical root, identity, permission set and role. Equal revision after explicit-role revoke rejects, including role-less downgrade/replay attempts. Higher valid revision imports without removing unrelated grants. Preserve legacy-only import behavior and record unrelated pre-existing issues separately; no repository-wide revision refactor. Keep defensive immutable copies for caller input.

- [ ] Write tests for positive mixed workspace/reference roles and requireGrant read/write/execute outcomes; frozen returned grants must not be mutable through input arrays.
- [ ] Write atomic-failure tests for malformed role, missing/non-directory root, duplicate-ID conflicts, alias duplicate under another ID, opposite-role parent/child both directions, overlap with prior state, and an unrelated valid entry before the failing entry. Assert list and subsequent revision are unchanged.
- [ ] Write idempotency tests for repeated identical requests and re-enrollment; same-role nested positive; explicit reselection advances once and revoke/re-enroll does not reuse an old epoch.
- [ ] Write import tests for role-less read and read/execute compatibility without widening; inconsistent explicit permissions denied; for explicit-role IDs, identical equal-epoch import allowed, changed fields/role-less downgrade denied, revoke then same-epoch import denied, higher-epoch valid import allowed. Do not expand these assertions into a legacy-only import redesign.
- [ ] Write deterministic interleaving test using a temporary filesystem adapter/stub only if needed: pause batch preparation, revoke or enroll another grant, resume and assert no stale resurrection/lost update. Avoid timing-only sleeps or tests of implementation internals.
- [ ] Build and run new targeted tests to record the failing assertions, then implement the minimal registry/type changes and rerun green.

Commands: `npm run build`; `node --test dist/test/workspace-roles.test.js dist/test/workspace-tools.test.js dist/test/grants.test.js`. Record the exact failing behavior before implementation and passing behavior afterward. Reuse unchanged native/VM evidence; these source tests do not certify native confinement or plugin integration.

## Task 2 — protected role persistence and durable revocation (next implementation)

**Files:** modify `src/local/grants.ts`; create `test/grants-roles.test.ts`. Reuse `WorkspaceRoleRequest`, `WorkspaceGrant` and `WorkspaceRegistry` from Task 1. No registry API expansion, MCP/native backend, identity configuration or live-store edits. All storage fixtures use private temporary directories passed explicitly as `dir`.

**Interface:** export `enrollRolesTrustedBatch(requests: readonly WorkspaceRoleRequest[], dir=identityDirectory()): Promise<Array<{id: string; root: string; grant: WorkspaceGrant}>>`. Return unique IDs in first-occurrence order with canonical roots. This is trusted role selection only; existing MCP `paths` behavior remains unchanged. Keep the existing `enrollReadOnly`, `enrollReadOnlyBatch`, `enrollExecute`, `loadTrustedRegistry`, `requirePersistedGrant`, and `revokeTrusted` signatures.

**Store contract:**

- Add optional `role` to the existing private `Entry` schema; preserve it in `asGrant`, enrollment serialization and revocation. Explicit active entries must be pinned and have exact role permissions (workspace read/write/execute, reference read). Explicit revoked entries remain pinned with role and empty permissions; never import them as active grants. Invalid role, unpinned explicit entry, or inconsistent active/revoked permissions fails closed as `INVALID_GRANT_STORE`. Do not infer a role from legacy permission arrays.
- Keep legacy unpinned entries inactive, pinned legacy permissions unchanged, and legacy enrollment/reselection revision behavior unchanged. Enrollment APIs must validate the final prospective set when explicit roles are present, so the older enrollment APIs cannot introduce opposite-role overlap or alias collisions around new role entries. Legacy APIs may reselect legacy-only IDs with their previous narrow permissions. If their requested ID already has explicit role metadata (active or revoked), reject with an actionable existing error directing the caller to explicit role selection; never silently drop that role, and never return a full workspace from a legacy read-only request.
- Under the existing cross-process grant lock, read and structurally validate the prior store; prepare the complete request batch through Task 1's role registry. Request cap remains 1–16; total store cap remains 128 including tombstones. Preserve unrelated entries/tombstones.
- Remove requested IDs from the retained candidate set before validating filesystem identities. Explicit reselection must recover a replaced/stale selected root without requiring the old selected path to exist or match its former inode. Retained active pinned roots still require identity validation. Unpinned legacy entries and tombstones receive no access and require no filesystem resolution.
- Validate the final candidate active set in a private registry using `importTrusted` before publication: aliases/physical duplicate roots and workspace/reference ancestor overlap fail; same-role nesting succeeds. Validation order must not turn a valid final replacement set into a false conflict. No partially built registry is returned on load failure; the existing fresh-local-registry/return-after-success pattern is sufficient.
- New selection starts revision 1; changed role/root/identity and explicit promotion of a legacy entry advance from its stored revision, including a revoked tombstone. An identical active explicit ID/root/role/identity/permission set is idempotent with unchanged revision. Duplicate identical requests collapse; conflicting duplicates reject. Reject revision overflow and invalid final sets before any store publication. Do not generate durable epochs from a newly created scratch registry's revision 1.
- `loadTrustedRegistry` round-trips roles on active pinned entries and returns only after all have validated. Durable tombstones remain in the store; they need not be imported into a new registry because new writes derive epochs from stored entries and persisted authorization rechecks read durable state. No new tombstone framework.
- Revocation only removes authority: retain protected-store and structural validation, advance the target's durable tombstone, and preserve unrelated entries. Do not resolve or revalidate unrelated root paths before revoking a target. A missing/replaced root in project B must not prevent revoking project A; ordinary full loading/enrollment still rejects stale retained identities. Revocation never repairs, rebinds or grants access to the stale root.
- `requirePersistedGrant` compares role as well as canonical root, identity, revision and existing permission comparison. A live explicit role changed to a legacy entry (or vice versa) at the same epoch yields `WORKSPACE_GRANT_CHANGED`; reference execution or revoked/missing entries remain denied. Preserve supported legacy read/execute behavior without adding writes or role metadata.
- Reuse protected ownership/mode/symlink checks, exclusive lock, private temp file, file sync, rename and directory sync. Before rename/publication, any failure leaves prior store bytes unchanged (or store absent if previously absent), and no success result/grant escapes. After rename, a sync/acknowledgement/cleanup failure may already have published the candidate: report `ConnectorError("RESULT_UNKNOWN", ...)` rather than claiming rollback or retrying. Preserve readable committed state; callers must read back before retry. Do not silently replace an error with success. No claim that fsync failure can be rolled back safely.

**Meaningful targeted tests:**

1. `mixed explicit roles survive store reload`: workspace/ref permissions and role metadata round-trip; reference write/execute denied; `requirePersistedGrant` returns workspace role.
2. `legacy grants retain prior behavior`: pinned read and read/execute remain role-less, unpinned legacy remains inaccessible, explicit trusted selection alone converts one to a role with an advanced epoch; legacy APIs retain their old revision semantics on legacy-only IDs. Legacy read-only/execute requests against an explicit-role ID reject without changing store bytes; unrelated legacy enrollment succeeds only when the final mixed set remains consistent.
3. `role batch duplicates and replay preserve epochs`: duplicate identical selections collapse and repeat idempotently; role change increments; revoke keeps role/empty permissions/tombstone, reload excludes it, re-enrollment exceeds the revoked epoch; overflow rejects before publication.
4. `failed mixed role batch preserves store bytes`: after a valid first candidate, invalid role, missing/non-directory root, conflicting duplicate ID, canonical/physical alias (even when both selections have the same role), opposite-role nesting both directions and final store capacity reject without publishing the prefix. Reloaded prior registry is unchanged. Same-role nesting is a positive control.
5. `reselection validates the final set`: replace a selected directory with a fresh directory, show ordinary load rejects stale identity, then explicit selection succeeds with a higher epoch; swapping requested IDs' roots is evaluated against the final set; unrelated stale retained roots still block publication.
6. `malformed explicit persisted entries fail closed`: invalid role, missing pin, active role/permission mismatch and revoked nonempty permissions; malformed later entry cannot return a partial loaded registry. Tombstones whose old paths disappeared remain valid metadata.
7. `persisted role downgrade invalidates active authorization`: change only stored role metadata to a structurally valid role-less legacy entry at the same revision and permissions; existing live explicit grant is rejected by `requirePersistedGrant`. Revoke/role changes also reject an old live epoch.
8. `publication failures are classified honestly`: deterministic filesystem failure before rename retains exact prior bytes and releases the owned lock; failure of directory sync after successful rename returns `RESULT_UNKNOWN`, readback shows the complete candidate, no second publication/retry occurs. Use scoped mocks restored in `finally`; never sleeps/timing guesses or live paths. Existing lock-busy/protected-store checks remain effective.
9. `revocation is independent of unrelated stale roots`: keep live A, replace B's root, revoke A successfully; raw store contains A's advanced role-preserving tombstone and unchanged B, while persisted authorization for live A rejects. Full loading remains blocked by stale B until explicit reselection; revocation does not widen access.

Write the new tests, record red against the missing API/behavior, implement the minimal store changes, then run `npm run build` and `node --test dist/test/grants-roles.test.js dist/test/grants.test.js dist/test/workspace-roles.test.js`. These targeted checks cover changed persistence plus legacy/registry integration; reuse unchanged native/VM evidence. Record exact errors and source hashes. Acceptance checks criteria §§3/7, no metadata loss/authority widening, whole-set validation, durable epochs and before/after-publication evidence. Task 2 does not establish a live-plugin or native capability pass.

## Task 3a — atomic registry application of persisted grants

**Files:** modify `src/core/workspace.ts`; extend `test/workspace-roles.test.ts`. No store, server or native changes in this slice.

**Interface:** `WorkspaceRegistry.replaceTrustedSnapshot(grants: readonly WorkspaceGrant[]): Promise<readonly WorkspaceGrant[]>`. Accept a complete active snapshot (0–128 grants), immutable results in unique-ID first-occurrence order. Existing single-grant imports retain compatible behavior; share validation where practical without rewriting unrelated legacy policy.

Validate complete input and pinned directories in an isolated prospective map, and check its final set once. This must allow a selected parent/child pair to change from both workspace to both reference without an intermediate mixed-role overlap, remove IDs absent from the durable snapshot, and replace roots that would alias stale local entries. Identical repeated grants collapse; conflicting same-ID grants reject. All existing explicit-history equal/lower epoch guards, revoked tombstones, immutable copies and overlap/alias rules remain. Preserve highest local revision and explicit-role history; each formerly active ID missing from the snapshot is revoked synchronously during commit and advances its local epoch once. Do not clear history by replacing private maps blindly. Durable tombstones remain the authoritative source for future persisted enrollment; this method does not manufacture access to missing IDs.

Recheck registry mutation generation after awaited preparation; any concurrent registry mutation rejects the entire replacement rather than losing updates or resurrecting revoked entries. Nothing changes until all preparation/validation succeeds, including revision overflow checks for removed IDs; commit synchronously to the original registry object captured by runtime closures. Empty snapshot clears active grants while retaining revocation history. Input is trusted complete durable state, never a user-supplied subset or role selection.

Tests: atomic parent/child role transition; complete snapshot removes an old ID and eliminates stale alias conflict; empty snapshot revokes; failure of later grant preserves all original entries/epochs; same-epoch authority change rejects; revoked replay and deterministic concurrent mutation reject; successful replacement updates the original object and old references observe its new state. Commands: `npm run build`; `node --test dist/test/workspace-roles.test.js dist/test/grants-roles.test.js`. This slice is a prerequisite for 3b; it does not complete plugin integration.

## Task 3b — plugin binding to protected roles

**Files:** modify `src/mcp/server.ts`, `src/mcp/runtime-bootstrap.ts`; modify `src/local/grants.ts` for structural root/ID metadata and, if needed, the trusted pre-publication authentication callback; create `test/mcp-workspace-roles.test.ts`; extend `test/runtime-bootstrap.test.ts` only for explicit identity-directory routing. Existing `test/mcp.test.ts` and `test/control-context.test.ts` are compatibility checks. No native or plugin installation changes.

**Input contract:** `bind_workspaces` accepts exactly one of:

- Legacy `{paths: [absolutePath, ...]}`: existing read-only role-less enrollment; never infer full workspace. Existing explicit-role ID at that root rejects with guidance to use the explicit form.
- Explicit `{roots: [{path: absolutePath, role: "workspace" | "reference"}, ...]}`: 1–16 entries, exactly `path` and `role` per entry. No user-supplied IDs. Entire outer object has exactly one form after stripping authenticated `control_token`. Reject empty, sparse, relative/NUL paths, unknown role/property, both forms, null/nonobjects and malformed members before any persistence/registry mutation. JSON schema expresses the two forms with `oneOf`, and runtime validation independently enforces them. Keep the existing token requirement added by `toolDefinitions`.

Resolve paths on the selected host. Report missing/not-directory/unavailable roots with the offending input index/path and an actionable reason; do not discover extra roots. Read structurally validated protected-store metadata for active root/ID mapping; do not call `loadTrustedRegistry` on the prior full set before reselection, because a selected root may have been replaced and is being explicitly repaired. Add `readTrustedRootBindings(dir=identityDirectory()): Promise<readonly {id: string; root: string}[]>` to `src/local/grants.ts`, reusing protected `readEntries` and filtering revoked entries without resolving old root identities. This trusted internal helper confers no directory access and is not an MCP tool. Match canonical selected paths to recorded root strings; final Task 2 persistence validation remains authoritative. Reuse an existing active canonical-root ID; otherwise use existing stable `ws-` plus first 16 lowercase hex SHA256 characters of canonical path. Canonical aliases share this ID and follow batch duplicate rules; conflicting roles reject. Repeated identical explicit binding preserves ID/revision. A same canonical root role change is explicit trusted reselection and advances its epoch. A previously unbound generated ID reuses its durable tombstone epoch through Task 2; never derive its epoch from the in-memory registry.

**Factory interface:** append optional `options: {grantDirectory?: string} = {}` after existing `controlStore` argument of `createReadOnlyTools`. Default remains the existing identity directory for production compatibility. Use the resolved directory for every bind/unbind/readback grant-store operation; `bootstrapMcpTools` passes `{grantDirectory: identityRoot}`. Tests always pass a private temporary directory and must not read/write the user's live identity. Existing factory callers remain source-compatible.

**Results:** bind entries include `workspace_id`, canonical `root`, `role` (`null` for legacy), `permissions`, `revision`. List/get include `role` alongside their existing fields; no need to expose additional paths there. Describe roles as granted intent. Add status metadata `workspace_roles: ["workspace", "reference"]` and `workspace_role_semantics: "grant-intent; backend-availability-reported-separately"` without changing existing truthful `hostFileWrites`, `readyForShell`, Git, VM execution environment or other capability flags. A full-workspace grant does not activate an unsupported file/shell/Git backend. Update bind/list/read descriptions so read tools are not misleadingly restricted to role-less workspaces.

**Mutation sequencing and uncertainty:**

1. Serialize bind and unbind operations per dispatcher with a local promise queue, including failure recovery of that queue. Do not serialize long-running jobs or control renewal behind it. Validate input before entering mutation work; production control authorization is checked again after queue wait and immediately before publication. Add an optional third argument `beforePublish?: (activeGrants: readonly WorkspaceGrant[]) => Promise<void>` to the two enrollment batch methods and `revokeTrusted`; execute it under the existing store lock after preparation/temp-file sync and before rename, without changing default legacy callers. Supply a defensive immutable snapshot of the complete prepared active grants, excluding tombstones/unpinned entries. The dispatcher captures that expected full set and rechecks the existing controller through this trusted internal callback; zero-argument callbacks remain compatible. This is authentication revalidation, not a new product approval gate; do not claim continuous controller fencing during filesystem awaits. A factory without a control store remains the existing test/composition seam, not a production authentication alternative.
2. Explicit binding calls Task 2's protected batch; legacy binding calls the existing read-only batch using the same directory. After either bind or unbind, load the complete durable active registry and apply its full active snapshot with Task 3a to the original registry, never sequentially or by replacing a local parameter/object reference. Do not merge only returned grants or retain ghost IDs absent from durable state. Unbind uses the same complete-snapshot path; no extra revoke loop or double epoch increment.
3. Read back durable active grants after publication and compare the entire set with the prepared snapshot captured under the writer lock, including unrelated IDs. Verify bound grant identity/role/permissions/revision or unbound absence, apply the complete snapshot, then re-read and compare the entire durable active set with the committed local set before returning success (IDs, roots, identity, role, permission sets and revision). A concurrent different publication, including one before the first readback, is not success for this call. Existing protected-store locking remains the durable writer lock; no cross-process transaction spanning registry memory is claimed.
4. Before-publication errors return their actual code and leave in-memory state unchanged. A `RESULT_UNKNOWN` from store publication, failure applying already-persisted grants, or inconsistent/failed post-publication readback returns `RESULT_UNKNOWN` and latches dispatcher scope state as desynchronized. Never auto-repeat persistence or claim rollback.
5. While desynchronized, reject subsequent scope-dependent calls (bind/unbind/list/get/read/files/Git/start/run/process/CI scope access) with `RESULT_UNKNOWN` and guidance to reload the protected registry in a fresh dispatcher. Keep connector status, global `list_capabilities` without a workspace argument, existing control acquire/renew/release, and existing owned `stop_process`/`ci_cancel` available so uncertainty can be diagnosed/stopped; retain their current permission/controller checks. Do not broaden stop authorization or fall back to stale grants. Recheck this latch after queued mutation waits too. Existing running native jobs retain durable grant/controller authorization checks; this task adds no new execution permission.

Role change of a parent/child pair succeeds as one final-set application to the original registry; a durable removal cannot leave a ghost local ID, and a valid fresh snapshot may replace a root conflicting only with stale local state.
