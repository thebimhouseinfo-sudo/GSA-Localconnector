# Mac file backend progression

**Status:** remaining Task 4 execution under the approved Mac-first scope; no milestone or acceptance advancement. The user requested remaining implementation before fresh tests on 2026-10-19. This document narrows the next implementation slice, not the approved goal.

**Goal:** connect proven Mac file primitives and permit reference/workspace file copy into a granted workspace without widening source authority.

**Architecture:** retain the signed per-root broker and protected installation proof. Compose a read from the source broker and an exclusive create through the destination broker. Never give one broker the union of source and destination write access.

**Tech stack:** existing TypeScript ESM, Swift broker and Node tests; no dependencies, VM, installation or global configuration changes.

**Spec:** [CRITERIA](../CRITERIA.md), especially §§3/7; Task 4 of [workspace roles plan](MAC-WORKSPACE-ROLES-PLAN.md). Execution stays manual through the existing harness. Push remains MANUAL_ONLY.

## Existing evidence and limits

`src/hosts/macos-scoped-files.ts` requires a signed, integrity-checked, host/root/revision-bound installation. That older limitation is resolved by source slice 4a: copyExclusive reads the source and exclusively creates the destination through their separate brokers. Installed/live acceptance remains pending. `src/mcp/write-dispatch.ts` already requires source read and destination write, with source write additionally required for move. The adapter is the narrower copy bottleneck.

`native/macos-files/broker.swift` implements stable bounded regular-file read, exclusive file create, mkdir and same-root exclusive file copy. It rejects symlinks, hardlinks and unsafe paths. The retained 2026-10-18 native characterization supports that exact subset and artifact only. Replace/move/trash explicitly fail with `SECURITY_BLOCKED_ATOMIC_COMPARE_UNAVAILABLE`; that failure remains intentional. New adapter/source work does not certify a new installed native artifact.

## Slice 4a: cross-root and reference file copy

**Owner files:** `src/hosts/macos-scoped-files.ts`; associated focused tests in `test/mac-scoped-files.test.ts` or the existing adapter test file if present. Preserve `NativeScopedFiles` signatures in `src/core/native-io.ts`. Do not modify broker operations or signed-proof requirements in this slice.

**Interface:** keep `copyExclusive(source: ScopedFileRef, dest: ScopedFileRef, expectedSha256: string): Promise<void>`. Consume the existing `read(ref, maxBytes)` and exclusive `create` operation; maximum remains 8 MiB.

1. Validate both relative paths and expected lowercase SHA-256 before starting I/O. Require source read and destination write. Reference source is allowed; reference destination and legacy read-only destination are denied.
2. Read and verify a bounded source snapshot through its bound broker. Match its hash to the caller's expected hash. Transfer exactly those bytes through the destination broker's `create` operation, which remains O_EXCL and never overwrites an existing entry. Preserve same-root file-copy semantics through this same composition if simpler.
3. Immediately before the destination create, recheck both grants against captured root identity/revision/permissions and call the production authorization callback for both IDs. A revoked or changed source must not be silently accepted merely because its bytes were already read. The destination invoke still verifies its own signed binding and authorization. There is no claim of an atomic transaction spanning two grants or continuous authorization across awaits.
4. On observed source hash conflict or pre-create authorization failure, create nothing. Exclusive destination collision must preserve the existing destination. Successful copy represents the verified source snapshot; later source edits do not make that snapshot invalid. Never remove or modify the source.
5. Once destination creation begins, preserve existing unknown-outcome errors on write/fsync/timeout/transport failure. A partial new file may exist; do not automatically unlink it because the name may have been changed by another writer. Do not claim rollback or auto-retry. Preserve the specific code so a caller can inspect the destination before deciding what to do next.

**Deferred fresh checks after implementation:** temporary fixtures only: reference-to-workspace and workspace-to-other-workspace positive copies; source unchanged; reference destination denied; source hash mismatch causes no create; existing destination preserved; source revocation/role/revision change between read/create denied; unknown destination outcome remains unknown. Reuse still-valid native broker evidence; only changed native behavior needs new native tests.

## Directory copy and destructive mutations remain separate

Directory copy is required by criteria, but `NativeScopedFiles` has no directory enumeration/copy interface. It cannot be implemented safely by recursive Node path I/O around the broker. A later native slice needs descriptor-relative enumeration and traversal, per-entry symlink/hardlink/special-file denial, bounded depth/entry/byte budgets, a caller-visible manifest/hash contract, exclusive destination creation and explicit partial-progress receipts. Listing a changing tree is not an atomic snapshot; report observed changes and partial output honestly. Do not add a directory tool that silently copies only regular files or claim Task 4 complete from Slice 4a.

The current broker blocks replace/edit/patch/move/rename/delete because its implementation has no safe compare-and-mutate strategy. This is an implementation restriction, not a product requirement for kernel content CAS. Criteria §4 requires actual-content editing, change detection and protecting user work; §8 explicitly permits UNKNOWN with reconciliation before retry. Neither requires zero pathname changes on every conflict or an immutable coherent snapshot against arbitrary external writers. A recoverable mutation design can satisfy those criteria without changing them. Advisory locks and a connector-only queue still do not constrain external writers; do not promise atomic content comparison or unconditional APPLIED.

## Slice 4c proposal: recoverable regular-file mutations

This is a source implementation proposal, not permission to alter live entitlements, install an artifact, generate a verification attestation or enable production writes before the changed boundary is tested. It replaces impossible-CAS reasoning with explicit preservation and outcomes. Existing `replaceIfHash`/`trashIfHash` void contracts alone cannot communicate these effects truthfully.

**Owner files:** `native/macos-files/broker.swift`, `src/core/native-io.ts`, `src/hosts/macos-scoped-files.ts`, `src/core/write-engine.ts`, `src/mcp/write-dispatch.ts`; add `src/core/file-transactions.ts` for typed outcomes and reconciliation dispatch. Tester owns focused tests after source implementation. Implement regular files first; directory deletion/move require a later tree contract and must reject before mutation.

**Native authority and recovery binding:** retain the App Sandbox fixed-operation broker. Add one dedicated connector-owned recovery root to each broker's signed binding, alongside that one workspace root; never grant it another project's root or launch project commands from it. The recovery root must be canonical, owner-only, on the same device as the workspace, with verified device/inode and protected ancestry. Signed metadata pins workspace ID/revision/root identity, recovery identity and artifact hashes. Reject a missing/different-volume/untrusted recovery root before any namespace change. Do not infer permission to provision recovery on an external volume or broaden to a parent directory. Source runtime provisioning and protected proof generation require their own installation implementation; self-generated checks cannot substitute for independent boundary evidence.

The retained-capture experiment explicitly ran unsandboxed (`test-retained-capture.py` lists that limitation); its ancestor-relocation escape refutes descriptor-only confinement, not this combined App Sandbox design. The original signed broker denied one ancestor-relocation create. That is useful prior evidence but does not prove the new capture/publish/recovery entitlements safe. There is no demonstrated impossibility of the combined design. The precise new boundary must be verified on disposable native fixtures before activation, especially a relocated workspace/recovery ancestor between validation and rename.

**Wire outcome contract:** `FileTransactionOutcome` carries `transaction_id`, `status: "APPLIED" | "CONFLICT" | "UNKNOWN"`, `operation`, source/destination refs, expected hash, observed hashes/identities, `effects` (captured/published/source-absent/destination-present as verified observations), opaque retained-version handles and an actionable reason. UNKNOWN never claims unchanged files. CONFLICT can carry verified partial effects; it is not synonym for no mutation. A trusted coordinator chooses a transaction ID, writes and fsyncs a durable intent before native mutation, and binds all retries/reconciliation to that ID. The existing controller/grant checks remain; no new approval gate is added. MCP returns structured outcomes instead of throwing away recovery details; old success receipts may be emitted only for a reconciled APPLIED result.

**Replace/edit/patch sequence:**

1. Validate fixed operation, bounded content, expected hash and no-follow relative path. Authorize and pin current workspace root/revision. Open workspace/recovery roots and parents with no-follow directory descriptors and verify their signed identities. Reject symlink/special/multiply linked source. Journal the intent; exclusively create a private transaction directory under recovery, leaving its capture leaf absent. Exclusively create the staging file inside that directory, then write and fsync new bytes. Caller supplies only a transaction ID and scoped file reference, never an arbitrary recovery path.
2. Read the target through a no-follow descriptor, hash bounded bytes and require the caller's expected hash. A mismatch before capture is a no-effect CONFLICT. Record the observed source identity. Recheck grants/controller and root/recovery bindings immediately before capture; OS sandbox enforcement remains required at each syscall despite those checks.
3. Capture the directory entry currently at the source name using same-volume exclusive rename into this transaction's unused recovery name. This can capture an entry substituted after the initial read. Open the captured name no-follow, record its identity/type and compare to the observed source identity and expected content. Preserve whatever was captured, including a mismatching entry; never unlink it as cleanup. A captured unsafe type is CONFLICT/UNKNOWN with actual namespace effects and no content traversal.
4. On mismatch, attempt restoration only with exclusive rename into the absent original name. If another writer recreated the name, leave both entries intact and return CONFLICT with the recovery handle. The check/open/restore gap cannot justify overwrite rollback. If a syscall, authorization, identity or acknowledgement is uncertain, return UNKNOWN and leave recovery intact.
5. On a matching capture, publish staged bytes only with exclusive/no-replace rename into the original name. A recreated name yields CONFLICT and preserves user, staged and captured entries. On publication success, retain the captured inode permanently until an independently defined explicit recovery/retention operation; an existing writable FD may continue modifying that retained inode. Do not call the retained version immutable. Record observed new identity/hash, flush namespace/journal as supported and reconcile before APPLIED. Any ambiguous acknowledgement or observed post-publication change yields UNKNOWN or a verified conflict outcome with effects, never an automatic repeat.

No algorithm can stop an unrelated editor destroying its own bytes. This design's obligation is that connector actions preserve captured/recreated entries and do not silently replace a detected different version. Post-operation file edits are separate observations; a successful bounded hash comparison verifies the bytes read, not an instantaneous source snapshot. Reconciliation must not convert later unrelated content into a claim that those exact bytes were originally published.

**Delete and move:** delete is capture plus validation with no replacement publication, leaving the retained source and opaque recovery handle. If capture fails its identity/hash check, use the exclusive restore/conflict sequence. This is connector recovery, not macOS Trash; criteria prefers recoverability and does not require the system Trash UI. No automatic permanent unlink or recovery garbage collection belongs to this slice.

For both same-volume and cross-volume regular-file move, define semantics explicitly as verified byte copy plus recoverable source removal; preserve late writes to the retained source inode and do not promise POSIX inode-preserving rename semantics. Destination creation is exclusive, using the already-defined copy boundary. After destination publication, capture/revalidate the source through its own same-volume protected recovery broker. A changed/recreated source leaves a partial outcome with the destination present and source/recovery effects recorded. Never delete the new destination as rollback and never retry automatically. Destination and source may reside on different devices, but each source capture requires source-volume recovery; no cross-device rename is attempted. If either participating broker/recovery binding is unavailable, reject before the first mutation. Reference sources are rejected for move/delete; only file copy permits them.

**Reconciliation:** add scoped `get_file_transaction` to return observed state for an existing owned transaction ID, under current controller and grants. Read protected journal and pinned native entry identities; inspect only original/staged/recovery names belonging to that transaction. Never execute another mutation or restore over a new name during readback. If ownership, durable intent, identity, scope or outcome cannot be established, preserve UNKNOWN and offer the existing opaque recovery handles. Repeated IDs with different arguments reject. Unknown IDs never manufacture a completed transaction.

**Deferred checks that control activation:** stable replace/delete and same/cross-volume move; hash mismatch before/after capture; substituted inode or unsafe file type; external recreation before publish/restore; open-FD late writes retained; duplicate transaction ID; crash before/after capture/publication/journal acknowledgement; journal fsync failure; permissions revoked between stages; root/recovery replacement and ancestor relocation around each native syscall; no reference/outside writes; source-volume recovery unavailable fails before effects. Reuse old evidence only for unchanged operations. A new entitlement/artifact requires targeted native confinement proof; unit/mock success cannot enable it.
